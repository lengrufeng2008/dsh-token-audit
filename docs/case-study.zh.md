# 我审计了 345 个 DSH 会话：钱到底花在哪了

> 数据来自一台真实的 DeepSeek Harness 安装，时间跨度 2026-09-22 至 2026-10-31。只统计 token 费用，不包含任何项目内容。工具开源、本地运行、不上传日志。

## 一句话结论

**¥778.78，22 个活跃日，折合每天 ¥35.40；按这个节奏一个月约 ¥1,062。** 其中 50% 是缓存读，38% 是输出，36% 发生在峰时。真正的大头不是“问得多”，而是“每次调用都带着很长的上下文”。

## 账单拆解

| 项目 | 金额 | 占比 |
|---|---:|---:|
| 缓存读输入 | ¥390.83 | 50.2% |
| 输出（含推理） | ¥297.36 | 38.2% |
| 缓存未命中输入 | ¥90.59 | 11.6% |
| 峰时时段 | ¥281.49 | 36.1% |

缓存读单价最低（闲时 ¥0.02/百万），但它是**每次调用都重新计费**的。上下文越长，这项越像“按次收的房租”。

## 还有一个数字：98% 的花费来自同一个工作区

不是均匀分布在所有项目上。先审计最贵的那个工作区，不要平均用力；把 Lean 模式用在那里，收益最大。

长期会话把上下文推到 50 万 token 以上，之后每一次工具调用、每一轮思考都按这个长度重读。压缩不是没开，而是默认阈值太高（窗口的 80%），等它触发时，已经贵了很久。

**2. 工具输出 78% 来自 bash。**

| 工具 | 字符量 | 占比 |
|---|---:|---:|

`cargo test`、`psql`、`tail -1`、`ls -la`、集群日志……单条被剪到 4k/1k，但条数太多，累计仍然可观。这不是模型的问题，是命令没有做输出预算。

## 如果重来一次，先改哪四刀

| 改动 | 估算节省 | 占比 |
|---|---:|---:|
| 上下文上限 250k | ¥118.90 | 15.3% |
| 输出压缩 20% | ¥59.47 | 7.6% |
| 40% 峰时任务挪到闲时 | ¥56.30 | 7.2% |
| 工具输出预算（bash 为主） | 未单独计价 | — |

合起来大约 **25–30%**，也就是每月 ¥250–320。注意这是“行为不变”的上限估算：压缩更早可能丢细节，输出更短可能多跑一步，必须用真实任务验证。

|---|---:|---:|---:|
| 费用 | ¥308.83 | ¥470.75 | +52.4% |

下半月不是单价涨了，是上下文更长、峰时更多。只看总花费会得出“花得多了”，只看单价会漏掉峰时；两个一起看才知道先改哪。

## 我做了什么

写了一个零配置 CLI：读取 `~/.dsh/sessions`，按官方峰谷价逐次调用计价，输出终端 / Markdown / HTML 报告。

```bash
npx dsh-token-audit
npx dsh-token-audit --format html --out audit.html --open
```

它同时是一个 DSH 插件，注册只读工具 `token_audit`，可以直接让 Agent 审计自己：

```bash
dsh plugin --profile web add dsh-token-audit
```

它还能直接生成 Lean 省流预设（`dsh-token-audit preset`），并在改动后用 `dsh-token-audit compare before.json after.json` 做前后对比。全部本地计算，无网络请求，无遥测。

## 三个诚实的限制

1. 这是估算，不是账单；订阅、赠送额度、渠道折扣都看不到。
2. 峰谷节假日只硬编码了中国 2026 年。
3. 上下文压缩是质量与成本的取舍，工具不建模质量损失。
